# September 14 Simulator repair

The latest candidate has now demonstrated visible units, selection, house construction, ground movement, sheep gathering, villager production, and a named save/reload in Simulator. Repeated ground movement and scout exploration also passed after a fresh launch; sustained frame pacing still needs qualification; this is not yet an end-user release.

## Proven root cause: changing resource filename casing

The staging script lowercased resources and widgetui names. This previously worked around other case-mismatched lookups, but broke animation lookups such as `u_vil_male_villager_idleA_x1.sld`. Host filesystem checks accepted both spellings while Simulator syscalls rejected the incorrect spelling. A host-only existence check concealed the failure.

The repair preserves original source names and verifies actual directory entries and file hashes. ResourceFileTrace now retries failed read/query operations using an immutable case-insensitive index limited to the imported AgeOfEmpires2Data root. The relay runner sets AGEPAD_CASE_INSENSITIVE_RESOURCE_ROOT. Writes, genuinely missing paths, denied accesses and paths outside the resource tree retain their original behavior. Do not mutate the resource tree during a game process; restart after replacing assets.

The existing staged tree was restored to source spelling without changing file contents. The restoration journal records paths, inode and size. The original source installation was not renamed.

## Proven input gap: only five hardware keys were forwarded

The old keyboard handler accepted Escape, period, H, F10 and F11, discarding ordinary letters and digits. The actual save dialog accepted H while the requested save name otherwise remained empty.

HardwareKeyMapping now maps US keyboard letters, digits, punctuation, navigation and F1–F12 to Mac virtual keys, preserves shifted text and base characters, and uses the same reverse mapping for polled key state. Standard editing keys go through the original responder's command handler. Native mapping tests pass. The actual touch translation/queue regression passed after including the new key-post helper in its fixture.

Live acceptance passed: actual hardware key presses created AGEPADFIX914, and a fresh launch loaded it successfully. AGEPADPLAY914 then preserved a completed house, population 8/10 and a working shepherd. Both saves have private hash manifests. This remains hardware keyboard support; an on-screen keyboard and international IME are not implemented.

## Rendering cost narrowed and reduced

The normal resource-fixed world measured 14 observed compositions in 10.020 seconds, with SLD hooks off. Another live window showed no new compressed uploads or SLD parses, excluding repeated animation decoding as the observed idle-scene bottleneck.

The sampled original game spends substantial time waiting on work. WidgetManager also performs substantial UI work. Sampling identifies where time is spent, not the defective synchronization primitive. Host load was uncontrolled; no physical iPad performance conclusion follows.

A sampled graphics call at executable offset 0xa55f00 resolves to `setFragmentSamplerStates:withRange:`. This ordinary sampler-array call still took the generic NSInvocation path. The candidate adds direct forwarding for sampler arrays and ordinary blend/stencil state calls. Argument-preservation tests pass, including sampler identities and nonzero index range, alongside existing texture/resource conversion checks. The matched sampler candidate is installed. A later normal run measured 221 compositions in 10.0265 seconds (22.04/s). Host load fell substantially at the same time, so the improvement cannot be attributed to this change alone. Short input intervals still encountered multi-hundred-millisecond stalls.

## Architectural decision

Keep the original ARM64 game route for now: the repaired Simulator has executed the actual simulation, movement, resource economy, construction, production and save/load. Today's evidence does not justify replacing that engine because of the earlier missing sprites or save-name failure; those were compatibility defects with concrete repairs.

Do not treat the Simulator runtime as a ready device runtime. Apple documents that Simulator translates Metal commands to the host GPU and has different feature limits, rather than emulating the selected iPad GPU. Our Simulator-only drawable notification implementation uses Simulator Core Animation behavior; device code needs the actual supported drawable API. The user's Simulator gameplay requirement remains the current functional gate. [Apple: Developing Metal apps that run in Simulator](https://developer.apple.com/documentation/metal/developing-metal-apps-that-run-in-simulator).

The download flow must also account for executable signing and Steam services. The current runner explicitly starts a host discovery relay and Simulator helper before launching the game; the helper is an operational dependency, not an installer detail. An importer cannot turn that arrangement into standalone play by copying assets. On iPadOS, executable code and linked libraries must pass code-signature validation; a user-data import cannot silently stand in for the signed runtime package. [Apple: App code signing process](https://support.apple.com/en-ca/guide/security/sec7c917bf14/web).

The next architecture gate is a device-built signed runtime with a declared service arrangement, after preserving this Simulator regression scenario. Reject claims of standalone downloadable play until that gate passes. Keep asset import, game execution, platform graphics support and service startup explicit in the supported flow instead of accumulating launch flags and treating one successful menu as completion.
